## 6. 캡션 지침과 로컬 LLM 실행 방식

캡션 지침은 `G:\fizgig\Fizgig_auto\automation\caption_instructions.txt`에 분리했다. 사진에서 확인할 수 있는 머리 모양, 옷과 색, 자세, 표정, 구도, 촬영 각도, 조명, 배경을 영어 약 60~100단어로 설명하도록 구성했다. 인물의 이름을 추측하거나 미적 평가를 붙이지 않도록 했다. 트리거는 실행기가 추가한다.

원본에 같은 이름의 비어 있지 않은 `.txt` 캡션이 있고 작업 사본의 캡션 파일이 없으면 우선 복사한다. 같은 작업 버전에서 이미 존재하는 비어 있지 않은 캡션은 재개 시 건너뛴다. 캡션 요청에는 EXIF 방향을 반영하고 최대 1024×1024 범위로 축소한 JPEG 이미지를 넣는다. 출력의 `<think>…</think>` 제거와 불완전한 응답 거부를 구현했지만, 모든 모델의 사고 과정 표식을 지원한다고 검증한 것은 아니다.

`local_caption.py`는 `http://127.0.0.1`, `http://localhost`, `http://[::1]`의 `/v1` 주소만 허용하고 프록시와 리다이렉트를 차단한다. 로컬 서버가 준비됐고 모델 별칭이 일치하면 재사용하고, 실행기가 직접 시작한 서버만 캡션 종료 후 닫도록 구현했다. 실제 자동 시작·캡션 생성·종료와 GPU 메모리 반환을 확인했다는 이전 기록이 있으며, 이번 재검토에서는 모델 서버를 다시 시작하지 않았다.

기존에 사용자가 실행한 서버는 자동으로 종료하지 않는다. `execute()`는 **설정한 캡션 주소의 포트가 열려 있으면** 캐시·학습 실행 전에 중단한다. GPU 사용량이나 전체 GPU 프로세스를 검사하는 것은 아니므로, 다른 포트의 LLM·ComfyUI 작업을 탐지하는 기능으로 해석하면 안 된다.

LLM 프로필에는 사용자 배치 파일, Q4_K_M GGUF 모델, BF16 mmproj 경로가 저장돼 있다. 최근에는 배치 파일 방식 외에 llama-server 실행 파일과 GGUF/mmproj를 직접 지정하는 방식도 추가했지만, 이 직접 실행 방식은 아직 검증하지 않았다.

## 7. TODO 및 학습 자동화 코드

`runner.py`에 다음 기능을 구현했다.

- `doctor`: Python·CUDA, 서버 준비 여부, 모델·실행 파일 경로와 데이터 목록 점검. 실제 캡션·캐시·학습 성공 검사는 아니다.
- `prepare`: 원본 사본 생성, 정확히 같은 파일 중복 제거, 손상 검사, 데이터 목록 저장.
- `caption`: 기존 캡션 재사용 및 부족한 사진의 로컬 캡션 생성. `--limit`으로 일부만 처리 가능.
- `plan`: 사진 준비 후 캡션·모델 조건을 검사해 네이티브 학습 명령을 `launch_plan.json`에 저장. GPU 학습은 실행하지 않지만 작업 폴더·manifest를 생성할 수 있다.
- `run`: 활성 TODO 작업의 캡션·캐시·학습을 순차 실행.
- `status`: 현재 설정·원본·지침으로 계산한 작업 버전의 `state.json` 조회. 과거 실행 폴더 전체를 나열하지 않으며 원본 폴더 접근과 정상 설정이 필요하다.

작업 버전은 병합된 설정 전체, 원본 경로·이미지 SHA-256·원본 캡션, 캡션 지침으로 계산한다. 따라서 학습률·스텝·LLM 대기 시간 같은 설정 변경도 새 작업 버전을 만들 수 있다. 이전 작업 폴더에서 캡션을 자동으로 찾아 이관하는 기능은 없다.

큐 잠금, 단계별 로그, 완료 단계 재사용, 마지막으로 완전히 저장한 학습 상태에서 재개하는 코드도 작성했다. 실제 캐시와 학습 재개는 아직 실행 검증하지 않았다. `state.json`은 캐시·학습 실행 과정에서 작성되므로, 캡션까지 완료돼 있어도 `status`는 `not started`를 표시할 수 있다. 캡션 완료 여부는 `images`의 파일과 사용량 로그로 따로 확인해야 한다.

**작업 사본의 캡션·이미지 수정은 버전 계산에 포함되지 않는다.** 완료 캐시 단계도 `state.json`의 이름만 보고 건너뛰므로, 캐시 이후 캡션을 편집하거나 캐시 파일이 손상·삭제됐을 때 자동으로 재생성된다고 보장할 수 없다. 캐시 무효화와 산출물 검증은 보완 과제다. `dataset_manifest.json`에는 전체 실행 설정 사본도 저장되지 않는다.

현재 TODO는 `eunbi_waterbomb` 1개이며, 트리거는 `eunbiwb`, 시드는 42다. 기본 데이터 폴더 외에 작업별 데이터 폴더와 목표 스텝·rank 등을 지정할 수 있다. 별도 승인 질문 없이 순차 처리하는 CLI 흐름을 구현했으며, 전용 승인·검수 상태를 관리하는 기능은 아직 없다.

### 복구 전 문제와 처리 결과

복구 전 `config.json`에는 다음 문제가 있었다.

```text
caption_model = gpt-4.1-mini
caption_base_url 등 로컬 연결 필수 설정 없음
```

복구 전 TODO를 `runner.settings()`에 넘겨 **`KeyError('caption_base_url')`를 실제 재현했다.** `doctor`, `prepare`, `caption`, `plan`, `run`, `status` 모두 이 설정 처리를 거치므로 환경 검사부터 정상 완료할 수 없었다. 설정 복구로 이 오류는 해소됐다. 다만 `runner.py`의 최상위 예외 처리는 여전히 `ValueError`, `RuntimeError`만 처리하므로, 필수 키가 다시 누락되면 친절한 설정 안내 대신 traceback으로 노출되는 코드 보완 과제는 남아 있다.

`G:\fizgig\Fizgig_auto\automation\llm_profiles.json`의 `Gemma 4 31B · 64K` 프로필을 기준으로 모델명을 `gemma4-31b-qat-uncen`으로 되돌리고, 로컬 주소·배치·GGUF·mmproj 경로·자동 시작·대기 시간을 `config.json`에 복구했다. 현재 프로필의 모든 키·값이 일치한다. 데이터 폴더, 목표 스텝, rank, 학습률, 샘플 프롬프트와 TODO는 유지했다. 과거 설정이 달라진 원인은 확인하지 않았다.

복구한 실제 설정과 현재 TODO로 `context()`를 계산한 결과, 기존 완료 폴더 `eunbi_waterbomb-d3a9b48e1970278f`와 정확히 일치했다. 사진 32장 각각에 비어 있지 않은 캡션이 있음을 확인하고 `captions()`를 호출해 `All captions already present; Gemma load skipped.`를 확인했다. 기존 산출물을 수정하거나 새 작업 버전을 만들지 않았다. `caption_launch_mode: "batch"` 같은 새 키를 추가하는 것만으로도 해시는 달라질 수 있어, 복구에는 프로필의 기존 키·값만 사용했다.

### 14.7 사람 점수 결과 — Krea2 구성 확정 (확인 완료, 2026-11-05)

시트에 사용자가 직접 채점했다(판정 93건, 그중 숫자 없이 `다른 캐릭터/심한 오류`만 표시한 25건). 점수는 **1 = 나쁨, 5 = 아주 좋음**이고, 추천은 가중 점수(정체성 0.45 / 지시 준수 0.30 / 품질 0.25)가 가장 높은 방식을 고른다.

| 방식 | 판정 | 정체성 | 지시 준수 | 품질 | 가중 | 다른 캐릭터/오류 |
| --- | --- | --- | --- | --- | --- | --- |
| **krea2_b_e028 (RAW+가속 LoRA+캐릭터 LoRA)** | 24 | 4.46 | 4.71 | 4.88 | **4.64** | 0 (0%) |
| krea2_a_e028 (Turbo+캐릭터 LoRA) | 24 | 4.08 | 4.71 | 4.88 | 4.47 | 0 (0%) |
| qwen_edit (툴2 기존 산출물) | 21 | 4.10 | 3.10 | 4.05 | 3.79 | 2 (10%) |
| krea2_c_e028 (레퍼런스 조건) | 24 | - | - | - | - | **24 (100%)** |

카테고리별 가중 점수: (b)는 각도 4.71·포즈 4.89·배경 4.49·표정 4.60·프레이밍 4.44로 모든 범주에서 (a)와 같거나 높다. (a)는 각도 4.42·포즈 4.55.

정체성이 갈린 16개 슬롯 중 **(b)가 12개에서 우세**, 특히 전신·측면·포즈에서 벌어졌다(`ang_front_wide` 4→5, `ang_back_medium` 4→5, `bg_park` 3→5, `pos_sitting`/`pos_walking`/`pos_waving` 모두 4→5). (a)가 나은 4개는 1점 차이였다.

**결론 3가지**

1. **구성 (c)는 탈락한다.** 24장 전부가 "다른 캐릭터"로 판정됐다. 스타일 레퍼런스 LoRA(`krea2_style_reference`)가 캐릭터 LoRA보다 강하게 작동해 정체성을 덮어쓴다. §4 M0의 "동작하면 포함하고, 안 되면 사유를 기록하고 뺀다"에 따라 **사유를 남기고 제외**한다. 그래프 빌더와 검사는 남겨 두므로, 나중에 LoRA 강도를 낮추는 방식으로 재시도할 수 있다.
2. **Krea2 경로가 툴2 Qwen 편집보다 낫다.** 지시 준수 4.71 대 3.10, 품질 4.88 대 4.05로 크게 앞서고 정체성도 동등 이상이다. 툴2는 원본에 앵커링된 편집이라 슬롯 지시를 잘 따르지 못하고, 전신(`ang_front_wide` 정체성 1점)과 측면·후면에서 무너진다 — §1.2의 추정이 데이터로 확인됐다.
3. **추천 구성은 (b) RAW DiT + 가속 LoRA + 캐릭터 LoRA** (가중 4.64). 다만 2위 (a)와의 차이가 **0.17로 자체 기준(0.2) 미만**이라, 시드를 늘리기 전에는 확정으로 보기 어렵다. 정체성(가중 0.45)에서 4.46 대 4.08로 앞서고 16개 슬롯 중 12개에서 우세한 점이 근거다.

**집계 버그를 하나 발견해 고쳤다.** 사용자가 숫자 없이 `다른 캐릭터/심한 오류`만 표시한 행(25건)을 `score_rows`가 통째로 버려서, (c)가 집계표에서 아예 사라지고 오류율도 낮게 잡혔다. 이제 오류 표시만 있는 행도 판정 수(n)와 오류율에 포함하고, 숫자 없는 건수를 `숫자 없음` 열로 따로 보여준다. 추천에서 제외된 방식은 `## 탈락` 절에 사유와 함께 명시한다.

**채점 UI도 사용자 요청으로 바꿨다.** 숫자 입력 대신 **1~5 버튼 클릭**(같은 숫자를 다시 누르면 해제)으로 바꾸고, 시트 상단에 "1 = 나쁨, 5 = 아주 좋음"과 가중치를 명시했다. 숫자 없이 오류만 표시하는 것도 정상 동작한다.

### 15.2 작업 버전과 캐시 분리 (확인 완료)

- `state.json`에 `family`/`arch_id`를 기록하고, 다른 family의 상태를 만나면 그 실행을 이어받지 않고 처음부터 시작한다고 알린다.

### 15.4 캡션 프로필과 정책 (구현 완료)

- `kind: photo | anime`로 지침 파일을 고른다. `photo`는 기존 `caption_instructions.txt`, `anime`은 새 `caption_instructions_anime.txt`(Danbooru 태그 + 문장, 툴2의 Qwen3-VL 프롬프트를 로컬 모델용으로 옮긴 것)다. 어느 파일을 썼는지가 캡션 식별자에 들어가므로, kind를 바꾸면 캡션이 섞이지 않고 새로 만든다.
- `caption_policy`:
  - `missing-only`(기본, 기존 동작): 캡션이 없는 이미지만 만든다. 있는 캡션은 건드리지 않는다.
  - `preserve`: 캡션을 새로 만들지 않는다. 캡션이 빠진 이미지가 있으면 조용히 만들지 않고 **사유를 밝히며 실패**한다(직접 손본 데이터셋을 덮어쓰지 않기 위해).
  - `explicit-recaption`: 모든 캡션을 다시 쓴다. 캡션 스타일만 다른 스냅샷 2개를 비교할 때(§7 Q4) 쓴다.

### 16.1 알려진 버그 2건 수정 (확인 완료)

`adopt()`가 **AI 캡션 딕셔너리**를 **손편집 여부 플래그**에 덮어쓰고 있었다. 하나의 이름이 두 가지를 가려서:

- 손편집 캡션이 기계가 쓴 것으로 보여 **재구성된 AI 캡션으로 덮어써졌다**.
- `autocaption.json`이 없거나 비면 기록 승계가 빠져, 나중에 태그를 고쳐도 그 캡션에 닿지 못했다.

두 사실을 다른 이름(`machine_written` / `auto`)으로 분리했다. 웹 UI는 `db.adopt(out_dir, back, t)`를 3인자로 호출하고 있었고(함수는 5인자) 그래서 번호가 바뀐 이미지를 복원하면 `TypeError`가 났다. 이제 `cfg, char`를 함께 넘긴다.

툴2의 **첫 검사 파일** `test_dataset_batch.py`를 만들었다(툴2 자체 인터프리터로 실행). **고치기 전 코드에서는 14개 중 6개가 실패**해 두 버그를 정확히 지목한다 — `adopt()` 관련 4건(기록 승계 누락 2건, 손편집 덮어쓰기 1건, 기록 없음 1건)과 앱 호출 2건(하나는 `(call='adopt', line=414)`로 호출 위치까지 알려준다). 고친 뒤 14개 전부 통과한다. `dataset_app.py`의 모든 `db.<함수>(...)` 호출이 `dataset_batch`가 선언한 인자 수와 맞는지 검사하는 항목도 넣었다 — 이런 종류의 버그는 사용자가 먼저 그 경로를 찾아야만 드러나기 때문이다.

### 16.2 재개 키 보강과 기존 데이터 마이그레이션 (확인 완료)

키에 **그래프 버전**(`GRAPH_VERSION = "qwen_edit21@1"`)과 **모델 파일의 내용 해시**(`quick_hash`: 크기+mtime+앞뒤 4MB, 작은 파일은 전체 sha256)를 넣고 길이를 6자에서 **12자**로 늘렸다. 모델 이름이 아니라 내용이 들어가므로 같은 이름으로 다시 내보낸 모델도 구분한다. 캡션은 키에서 빠져 있어 태그만 고치면 이미지는 재생성되지 않는다(검사로 고정).

**기존 데이터셋이 재생성되지 않는다는 것이 핵심이다.** 옛 공식(모델 *이름* 기반 6자)을 `legacy_png`/`legacy_job`으로 함께 계산해 두고, 새 이름의 파일이 없으면 옛 이름의 파일을 `adopt()`한다. 실제 `dataset/수아맘`(55장)에 대해 계획을 돌린 결과 **55개 작업 전부가 옛 파일을 찾았고 재생성 대상 0건**이었다. 복사본에 실제 CLI를 돌려 **55장 전부 "adopted from the previous key length"로 건너뛰고 생성 0건**, 파일 55개가 12자 키로 바뀌고 캡션 55개가 그대로 남는 것을 확인했다.

기각 이력도 유지된다: 파일명만 보면 키가 바뀌어 기각한 이미지가 되살아나므로 작업 판정은 `legacy_job`까지 함께 본다(검사 있음). 실제 데이터셋에는 `_rejected` 폴더가 없어 해당 사례는 없었다.

### 16.3 부분 저장 방지와 prompt_id 영속화 (확인 완료)

- 이미지·JSON은 임시 이름에 쓴 뒤 `os.replace`로 확정한다. 반쪽 PNG는 없는 것보다 나쁘다 — `png.exists()`가 "이미 했다"의 근거이므로 반쪽 파일은 영원히 건너뛰어지고 학습에 들어간다.
- `_pending_prompts.json`에 **제출 직후** prompt_id를 기록한다. 중간에 죽으면 다음 실행이 `/history`에 물어보고, 이미 만들어진 그림은 내려받아 저장하고 **다시 제출하지 않는다**. 서버가 모르는 id(재시작)면 기록을 지우고 정상 재생성한다. 파일이 저장된 뒤에는 기록을 지운다(검사에서 이 누락을 잡아 고쳤다).

### 16.4 프로세스 간 잠금 (확인 완료)

`FolderLock`이 출력 폴더에 PID·시각·명령을 적는다. 살아 있는 소유자가 있으면 거부하고, 죽은 프로세스의 잠금은 회수한다. 같은 프로세스의 두 번째 기록자도 거부한다(중첩 실행이 서로 파일을 rename하는 것을 막기 위해). `run_dataset`/`run_captions`에 데코레이터로 붙여 **CLI와 웹 UI가 각자 기억할 필요 없이** 보장된다. 웹 UI의 `busy_with()`는 *다른* 프로세스가 잡은 잠금을 보고 거부한다(자기 작업은 기존 JOB 검사가 담당).

### 16.5 자동화용 CLI (확인 완료)

| 옵션 | 내용 | 실제 확인 |
| --- | --- | --- |
| `--result-json PATH` | 버전 있는 결과 JSON(생성/스킵/실패 목록, 파일, 파라미터) | `version=1`, `graph_version=qwen_edit21@1`, planned 55 / skipped 55 |
| `--events` | stdout에 JSON Lines, 사람용 로그는 stderr로 이동 | stdout이 **정확히 57줄의 JSON**(run 1, image 55, summary 1), 산문 없음 |

| `--fix-jobs PATH` | `[{input, refs[], prompt, seed, out}]` — image1=고칠 그림, image2..n=원본 레퍼런스, consistency LoRA | **실제 GPU: 42초, 1.4MB PNG 생성**, 결과 JSON에 파라미터 기록 |

결과 행에는 `seed`/`prompt`/`steps`/`cfg`/`resolution`/`lora`/`refs`가 들어가 호출자가 툴2의 manifest를 읽지 않고도 후보를 기록할 수 있다. 여기서 **버그를 하나 더 잡았다**: 캡션 대신 작업 딕셔너리를 결과 행에 넣어 `Path` 객체가 JSON 직렬화에 실패했다(검사가 잡음).

`--fix-jobs`/`--config`는 사람이 쓰는 파일이므로 **BOM을 허용**한다(`utf-8-sig`). 실제 실행에서 PowerShell이 쓴 BOM 때문에 실패해 드러난 문제다. 캡션·manifest·autocaption 읽기도 함께 관대하게 바꿨다.

### 16.6 생성기 A: 툴1 ↔ 툴2 연결 (확인 완료)

`automation/pipeline/gen_qwen_edit.py`. 프로젝트 설정으로 **실행별 스냅샷**을 만들어 툴2 CLI에 넘기고 결과를 `candidates.jsonl`로 들여온다.

- 스냅샷은 툴2 설정, 캐릭터 항목, **입력 이미지 바이트**, 툴2의 그래프 버전을 묶어 id를 만든다(`sha256[:12]`). 입력은 복사하므로 나중에 원본을 고쳐도 이 실행의 결과가 달라지지 않는다.
- 툴2의 그래프 버전은 **툴2 소스에서 직접 읽는다**(`GRAPH_VERSION`). 코드를 복사하지 않고 상수 하나만 읽는 것이라 D1에 어긋나지 않는다. 실패하면 "unknown"으로 기록하고 추측하지 않는다.

- 계보: 후보는 세대 1, 편집 깊이 1, `parent_ids`는 스냅샷 안 원본의 source id다. 실제 실행에서 16개 입력(합성 1 + 원본 15) 중 부모가 스냅샷 source로 해석되는 것을 확인했다.
- 홀드아웃용 `exclude` 인자를 미리 지원한다(§7 Q6에서 사용).

실제 실행: `--only framing --limit 1` → 스냅샷 `b4e7b971906f`, 툴2가 1장 생성, 후보 1건 기록(`graph_version: tool2:qwen_edit21@1`, 부모 1개 해석).

- **원본 판정은 폴더가 아니라 기록으로 한다.** tool2의 `set_anchor()`가 합성 앵커를 `characters/<name>/`에 넣기 때문이다. 카드의 `synthetic_sources`가 1순위, 없으면 tool2 자신의 후보 파일 접두사(`anchor_refined_` 등)를 근거로 삼고 **판정 근거를 함께 기록**한다.
- 원본은 내용 해시 이름(`<sha256[:16]>.<ext>`)으로 복사하며, 같은 내용이 두 이름으로 오면 한 건으로 본다. 원본 바이트는 건드리지 않는다.
- 홀드아웃(§7 Q6): 사용자 원본이 `holdout.min_sources`(기본 15) 이상일 때만 자동으로 뺀다. 카드가 파일명을 지정하면 그것을 우선하고, 없으면 정면 1장 + 다음 1장.
- 검수 결정(`accept`/`reject`/`fix`)과 슬롯별 쿼터 집계. `accepted(limit_generation=...)`로 세대 상한을 적용할 수 있다.
- 프로젝트 잠금(`pipeline.lock`): 다른 살아 있는 프로세스가 잡고 있으면 거부하고, 죽은 프로세스의 잠금은 회수한다.
- 후보 들여오기: `import_candidates(records, base=...)`가 이미지를 `candidates/<generator>/<batch>/`로 복사하고 내용 해시로 이름을 붙인다. **`base`가 필요한 이유**: 이전 실행이 기록한 `file`이 그 실행의 폴더 기준 상대 경로일 수 있어서, M0 실험의 후보 21건을 들여올 때 이것 때문에 한 번 실패했다.

### 18.1 T1 — 시드 입력 자격과 홀드아웃 격리 (`pipeline/seed.py`, `pipeline/project.py`, `pipeline/gen_qwen_edit.py`)

- **`seed.audit()`가 자격 판정의 단일 지점**이다. source와 candidate 각각에 대해 `kept` 또는 `excluded` 한 줄을 돌려주고, 제외는 **사유 코드 + 문장 + 대처**로 남긴다(`EXCLUSIONS` 표). 코드는 `holdout_source`/`holdout_direct`/`holdout_indirect`/`holdout_via_lora`/`missing_parent`/`cyclic_lineage`/`unverified_ancestor`/`no_ancestry`/`lora_snapshot_unverified`/`synthetic_source`/`not_reviewed`/`rejected`/`marked_for_fix`/`different_character`/`generator_not_eligible`/`generation_cap`/`edit_depth_cap`/`missing_file`/`tampered_file`/`duplicate_bytes` 20종.
- **입력은 사용자 원본 + 채택된 `qwen_edit`만.** 합성 source(앵커)는 원본이 아니므로 제외하고, 그 앵커에 **부모 기록이 없으면 격리**한다(`quarantined`). 격리된 앵커를 조상으로 둔 후보는 `unverified_ancestor`로 함께 제외한다 — 앵커의 출처를 복원할 수 없으면 그 앵커가 홀드아웃에서 나왔을 가능성을 배제할 수 없기 때문이다.
- **계보 검사**는 `seed.walk()`가 부모를 끝까지 따라가며 (조상, 미확인 부모, 순환)을 돌려준다. 직접 부모의 홀드아웃(`holdout_direct`)과 조상의 홀드아웃(`holdout_indirect`)을 구분해 보고한다. LoRA로 만든 이미지는 `trained_on_snapshot`을 프로젝트의 스냅샷 manifest와 대조해, 그 스냅샷이 홀드아웃을 품었으면 `holdout_via_lora`, 기록을 찾을 수 없으면 `lora_snapshot_unverified`로 막는다.
- **바이트 검증**: 디스크의 실제 SHA가 기록과 다르면 `tampered_file`, 파일이 없으면 `missing_file`.
- **한 그림은 한 장**: 자격을 통과한 입력을 SHA로 묶어 대표 1건만 남기고, 같은 바이트의 모든 계보 ID를 `lineage_ids`에 보존한다(`duplicate_bytes`).
- **홀드아웃 동결**: `Project.holdout_entry()`가 `ids`/`files`/`shas`를 카드에 동결한다(`freeze_holdout`). 한 번 동결하면 원본을 더 들여오거나 이름이 바뀌어도 집합이 움직이지 않는다. 실제 프로젝트에 적용했다(18.4).
- **생성기 A도 같은 규칙을 쓴다**: `gen_qwen_edit.build_snapshot()`이 카드의 동결된 홀드아웃을 **이름과 내용 해시 양쪽으로** 입력 폴더에서 빼고, 그 사실을 스냅샷의 `config.json`(실행별 설정의 `excluded_inputs`)과 `snapshot.json`(`excluded_detail`)에 함께 기록한다. 카드가 레퍼런스로 지목한 파일이 제외되면 **계획 단계에서 경고**한다(`missing_references`).
- **M0 유래 결정 구분**: `review.json` 각 항목에 `origin`(`m0_score`/`user`)을 남긴다. `decide(by="user (M0 scores)")`가 자동으로 `m0_score`를 붙이고, `audit()`의 `accepted_from_m0`/`accepted_by_review`로 갈라 센다.

### 18.2 T2 — 스냅샷 무결성과 재실행 (`pipeline/seed.py`)

- **경로 해석**: `Project.resolve_file()`이 프로젝트 기준·`automation/` 기준·절대 경로를 모두 받는다. 그래서 작업 루트에서 돌리든 툴1 폴더에서 돌리든 같은 결과가 나온다(18.5에서 실제 확인).
- **ID가 캡션과 정책까지 묶는다**: `snapshot_identity()`는 프로젝트 카드 digest, `policy`(`seed-v1`), lineage 상한, 홀드아웃 SHA, 그리고 **(이미지 SHA, 캡션 SHA) 쌍**을 해시한다. 그래서 캡션 정책을 바꾸면 새 ID가 되고, 같은 입력·같은 캡션은 같은 ID가 된다.
- **임시 폴더에서 검증 후 게시**: `seed_lora/<id>.tmp-<pid>-<rand>/`에 이미지·캡션·`snapshot.json`을 쓰고, `validate_snapshot()`(고유 SHA 수 = manifest 입력 수 = 디스크 이미지 수 = 캡션 수, 각 이미지의 실제 SHA, 캡션 SHA)을 통과해야만 `os.replace`로 `seed_lora/<id>/`가 된다. 실패하면 임시 폴더만 지운다.
- **재실행은 지우고 다시 만들지 않는다**: 이미 게시된 ID가 있고 검증을 통과하면 `reused: True`로 그대로 돌려준다(파일 mtime 보존). 검증에 실패하면 **아무것도 덮어쓰지 않고** 무엇이 깨졌는지와 복구 방법을 문장으로 남긴다.
- **캡션 충돌**: 같은 바이트에 서로 다른 캡션이 붙어 있으면 고른 캡션·출처·후보들을 `caption_conflicts`에 남긴다.
- 합성 비율은 **고유 이미지** 기준으로 다시 계산한다(19/32 → 0%).

### 18.3 T3 — 검수 웹: 보이는 이미지와 저장되는 결정 (`pipeline/review.py`, `pipeline/project.py`)

- **URL과 라우트 통일**: 페이지는 `/image/<id><파일 확장자>`를 내보내고 서버는 그 경로를 그대로 받는다(확장자를 뺀 요청도 계속 동작). MIME은 파일 확장자에 맞춘다(`png`/`jpeg`/`webp`). 페이지가 그린 URL과 서버가 답하는 URL이 같은 함수(`review.image_url`)에서 나온다.
- **구조화된 사유**: `review.json` 항목에 `reason`(`different_character`/`wrong_style`/`artifact`/`other`)을 저장한다. 페이지에 **"다른 캐릭터"(D)** 버튼을 추가했고, 그 사유가 붙은 이미지는 **채택·보정이 서버에서 400으로 거부**된다(기각만 가능). 행의 `fixable`은 이제 실제 값이다(전에는 `mark != "reject" or True`로 항상 참).
- **이력 마이그레이션**: `Project.review_plan()`/`migrate_review()`가 `note` 문장에서 "다른 캐릭터"를 찾아 `reason`으로 옮기고, 모든 항목에 `origin`을 붙인다. **쓰기 전에 변경 건수와 이유를 먼저 출력**한다(`--migrate-review`, `--apply` 없이는 미리보기).
- **거부 규칙**: 존재하지 않는 id는 400(`존재하지 않는 후보입니다`)이며 `review.json`에 흔적을 남기지 않는다. 사유·결정 값 검증도 서버가 한다.

## 19.5 첫 배치 12장은 전부 "한 그림에 두 명" — 원인과 수정 (2026-11-06 16:00~16:20)

사용자가 검수 중에 "새로 만든 이미지는 1장에 2명씩 나오지 전부 다 그렇네"라고 알려 왔다. 12장 전부 같은 결함이었고, 원인은 세 가지가 겹친 것이었다.

### 19.5.1 원인 (코드로 확인)

1. **`use_extra_refs`가 expressions/backgrounds에서는 읽히지 않았다.** `plan_jobs()`가 이 두 범주의 `job()` 호출에 `extra=True`를 **하드코딩**하고 있었다(설정은 framing/poses에만 적용). 그래서 이 두 범주는 설정으로 참조를 끌 수 없었다.
2. **참조 2장이 임의의 다른 원본으로 대체됐다.** `pool = close_bases if len(close_bases) > 1 else close_bases + files` — 홀드아웃이던 `edit_bases` 2장을 T1에서 제거해 `close_bases`가 1장이 되자 폴백이 발동해, 캐릭터 폴더의 아무 원본(뒤에서 앉은 전신샷 포함)이 "같은 캐릭터 참조"로 들어갔다. tool2 주석이 이미 경고하던 지점("같은 옷의 얼굴 기준이 아닌 다른 원본은 다른 옷·표정을 끌어온다")이다.
3. **프롬프트에 "한 장에 한 명"이 없었다.** 일반 참조 문구는 "Image 1 = 편집 대상, images 2~3 = 참조"까지만 말했고, "Output one single image, not a side-by-side comparison"은 각도/측면 문구에만 붙었다.

### 19.5.2 수정 (두 개의 손잡이 + 실행별 설정)

- **`use_extra_refs`가 실제로 동작한다**: expressions/backgrounds가 `cfg[section].get("use_extra_refs", True)`를 읽는다. **기본값은 지금과 같은 켜짐**이라 기존 데이터셋·잡 키는 그대로다.
- **`one_image` 설정**: `ref_note(..., one_image=True)`가 일반 참조 문구 뒤에 "Output one single image of the character in image 1, drawn once, not a split screen, a comic panel or a side-by-side comparison."을 붙인다. 참조가 1장이면 아무 일도 하지 않고, 각도 문구와 중복되지 않는다. **켜야 하는 설정**인 이유: 프롬프트가 바뀌면 다중 참조 잡의 키가 전부 바뀌어 기존 데이터셋이 재생성되기 때문이다.
- **실행별 설정은 스냅샷에만**: `gen_qwen_edit.build_snapshot(..., sections=...)` + `--set section.key=value`. 스냅샷 ID가 설정을 포함하므로 설정이 다르면 다른 폴더가 되고, `snapshot.json.section_overrides`에 무엇을 바꿨는지 남는다. **`dataset_jobs.json`은 손대지 않았다**(사용자 승인 없이 툴2 설정을 바꾸지 않는다는 규칙 유지).

## 20. M3-4 보정(C) — `fix` 판정만 툴2로 보내고, 결과는 새 후보로 (`pipeline/fix.py`)

### 20.1 계약

- **`fix` 판정만 대상**: `plan()`은 `review.json`에서 `decision == "fix"`인 후보만 모은다. 페이지 새로고침·계획 실행은 GPU를 쓰지 않고, 점수가 낮다는 이유로 자동 보정하지 않는다.
- **원본은 건드리지 않는다**: 보정 결과는 `parent_ids`에 고친 후보를 두고, **세대는 그대로**, **편집 깊이는 +1**인 새 후보로 등록된다.
- **홀드아웃은 참조가 될 수 없다**: `--refs originals`일 때만 원본 참조를 붙이고(동결된 홀드아웃은 이름·해시로 제외), 기본값은 `--refs none`. 참조를 안 붙이는 편이 "두 명" 재발도 막는다.
- **프롬프트**: 검수 항목의 `note`가 있으면 그것을, 없으면 `DEFAULT_FIX_PROMPT`("한 장에 한 명, 인물·포즈·배경 유지, 선화·손·중복 인물 교정")를 쓴다. 페이지에 메모 입력이 없어서 F만 누른 경우가 여기 해당한다.
- **차단 사유를 남긴다**: `다른 캐릭터` 판정(보정 불가), 파일 없음, 홀드아웃 원본은 `blocked`로 보고하고 조용히 건너뛰지 않는다.
- **배치 ID = (대상·프롬프트·참조) 해시**: 같은 계획을 다시 돌리면 같은 폴더이고, 툴2의 `<out>.fix.json` 사이드카 덕분에 **재실행 시 신규 제출 0건**이다.
- **캡션**: 툴2의 보정 모드는 캡션을 쓰지 않으므로, 보정본은 **고친 그림의 캡션을 물려받는다**(출처도 함께 기록). 아직 캡션이 빈 기존 보정본 7건은 backfill 했다.

## 21. 구도 중심 데이터셋 — 전신·측면·포즈·의상·배경 (2026-11-06 17:00~)

사용자 지적: "데이터셋이 목적인데 표정에 집착하지 말고 측면샷이나 cowboy shot처럼 더 다양한 구도가 좋지 않겠니" →

### 21.1 전신·카우보이·포즈는 전신 앵커에서 시작한다 — 그 앵커의 출처는 복원 불가

`plan_jobs()`에서 `body = d != "close-up"`이므로 **medium(cowboy)·wide 각도, full-body/dutch 프레이밍, 포즈 전부가
`body_bases`(전신 앵커)에서 시작**한다. 그 앵커(`anchor_refined_fullbody_d_00020__e7417d_s1001.png`)는 `origin: synthetic`,
`parent_ids: []`인 채로 프로젝트에 들어왔다.

**복원 시도와 결과**: tool2는 전신 후보를 `fullbody_<refid>__<key>_s<seed>`로 이름 붙이고, `key = sha1(prompt + 입력
바이트들)[:6]`이다. 설정(`fullbody_source` + `figure_refs` + 프롬프트)으로 **재계산한 키는 `495d78`, 파일명은 `e7417d`** —
일치하지 않았다(당시 설정이 지금과 달랐다). 그래서 **부모를 기록하지 않았다**(추정 금지). 확인된 것만 적으면:
`_fullbody_candidates/refined_…_s1001.png`와 캐릭터 폴더의 앵커가 **바이트 동일**(3,131,273B)이므로, 앵커는 그 refined
후보를 채택한 것이고, refined의 입력은 미세련 앵커(`fullbody_d_00020__e7417d_s1001.png`, 840KB) + `fullbody_source`다.
그 미세련 앵커의 입력이 복원되지 않으므로 사슬은 미확인에서 끝난다 → **앵커는 격리 유지, 파생물은 시드 부적격.**

**따라서 전신·포즈 이미지는 "최종 데이터셋용"으로 만들고, 시드에는 넣지 않는다**(감사가 `unverified_ancestor`로 표시).
시드에 넣으려면 앵커를 **비홀드아웃 원본에서 새로 생성**해 출처를 파이프라인이 기록하게 해야 한다(다음 작업).

### 21.2 의상 — 카드에 `outfit_hint`가 없었다

### 23.1 결함 A — `fix.plan()`이 이미 보정본이 있는 원본을 다시 계획했다 (툴1, 실제 GPU 낭비)

`fix` 판정은 **원본에 남는다**. 보정본을 만든다고 원본의 판정이 바뀌는 것이 아니므로, 다음 실행도 그 원본을
"보정 대상"으로 다시 본다. 실제 프로젝트에서 8건을 계획했는데 **7건은 이미 보정본이 있었다**(배치 `8b5f2547f596`).
게다가 배치 id는 잡 목록에서 나오므로 새 실행은 다른 폴더(`02f6c504bb51`)가 되어, 기존 사이드카의 재사용 방어도
걸리지 않는다 → **7장을 그대로 GPU에 다시 올린다.**

수정: `corrections_of(project, target_id)`로 이미 등록된 보정본을 찾고, 있으면 `already`로 **따로 보고**하고 잡에서
뺀다. `already`는 실패가 아니므로 `blocked`와 분리했다. 정말 두 번째 보정이 필요하면 `--redo <id>`로 **사람이
지목**한다(그림을 다시 그리는 일은 부작용이 아니라 결정이어야 한다).

검사: 툴1 **354개 통과**(+4: 이미 보정본이 있으면 다시 안 그림 / 마지막에 표시한 1건만 계획 / `--redo`는 예외 /

### 23.2 결함 B — 보정이 원본 화소를 절반으로 깎았다 (툴2 + 툴1, **화질 손실**)

다른 사투리로 물으면 **프롬프트를 측정하게 된다**. 크기는 `krea2_inference.size`(1024×1536)를 그대로 써서
한 행이 **해상도 변화가 아니라 체크포인트 차이**를 보여주게 했다.

표는 **행=프롬프트, 열=에포크**다. 질문이 "이 포즈를 어느 에포크가 잘 그리나"이고 그건 가로로 읽어야 답이 된다.

### 24.3 기록은 네 가지를 구분한다

`choose --epoch N`은 **run ID / 체크포인트 파일+SHA-256 / 학습 snapshot ID / 평가 조건**을 따로 남긴다. 에포크
숫자만으로는 어느 런의 것인지 알 수 없고, 런은 재학습될 수 있다. SHA-256은 **판단한 바이트를 고정**하고,
snapshot은 그 체크포인트가 **무엇을 배웠는지**를 남긴다 — 나중에 생성물을 시드까지 추적하는 근거다.

`choose`는 그리드에 없던 에포크를 거부하고, 계획 후 **바이트가 바뀐 체크포인트**도 거부한다(아무도 안 본 파일에
판단을 붙이는 것이 기록 없음보다 나쁘다).

## 26. M4 점수·불변 export·홀드아웃 평가 (2026-11-06 19:00~20:05)

명세 3.5(불변 export)·§4(점수)·M4(홀드아웃). 다섯 파일이 늘었다:
`pipeline/scorers/{__init__,clip_vision,common,arcface}.py`, `pipeline/export.py`, `pipeline/evaluate.py`,
`pipeline/score.py`. 툴1 테스트 **420 → 507**(+87).

### 26.1 이 단계의 핵심 질문은 "점수가 사람과 맞는가"였다

명세는 점수를 **표시용**으로만 쓰라고 한다(자동 기각 금지). 그렇다면 점수가 쓸모 있는지는
**사람이 매긴 점수와 비교해서만** 답할 수 있다. M0 사람 시트가 93행 있으므로 실측했다.

| 비교 대상 | 상관(Spearman) |
|---|---|
| CLIP `max_cosine` vs 사람 `identity` | **+0.038** |
| CLIP `max_cosine` vs 사람 `instruction` | +0.237 |
| CLIP `max_cosine` vs 사람 `quality` | +0.182 |
| CLIP `max_cosine` vs 사람 가중 총점(0.45/0.30/0.25) | +0.174 |
| ArcFace `max_cosine` vs 사람 `identity` | **+0.149** |
| CLIP vs ArcFace (같은 쌍) | +0.341 |

**결론: 두 점수기 모두 사람의 정체성 판단을 거의 따라가지 못한다**(CLIP +0.04, ArcFace +0.15).
CLIP은 오히려 **지시 준수·품질**과 더 상관한다 — 즉 "이 캐릭터인가"가 아니라 "이 세트처럼 보이는가"를 잰다.
그래서 **둘을 평균해 하나의 '정체성 점수'로 만들지 않는다**. 서로 +0.34밖에 상관하지 않는 두 수를
합치면 어느 쪽이 무슨 말을 했는지 지워진다.

### 26.2 처음 잰 -0.45는 점수기가 아니라 내 페어링 버그였다

첫 측정에서 상관이 **-0.45**(측면·후면은 -0.68)로 나왔다. 점수가 사람과 **반대로** 움직인다는 뜻이라
그럴듯했지만, 원인은 프로브였다: 시트의 `task` 열은 `<slot>__<method>__s<seed>`인데
**slot을 버리고 method+seed만으로** 이미지를 찾아, 같은 method·seed를 쓰는 다른 슬롯의 사진을 집었다.
후보 레코드의 `file`이 `images/<method>/<slot>__s<seed>.png`이므로 **경로에서 키를 그대로 재구성**해 고쳤고,
상관은 +0.17로 돌아왔다. **음의 상관은 데이터가 아니라 내 실수였다** — 이 사실을 먼저 적는다.

### 26.3 그래도 점수를 쓰는 이유와 쓰지 않는 이유

- **쓴다**: 검수 페이지에서 **정렬**할 수 있다. 98장을 눈으로 다 보는 대신 CLIP 하위 20장부터 볼 수 있다.
  이것은 사람의 판단을 **대체하지 않고 순서만** 바꾼다.
- **쓰지 않는다**: 자동 기각·자동 채택. +0.04 상관으로 기각하면 사람이 채택할 사진을 버린다.
- **얼굴 검출 실패는 0점이 아니라 "없음"**: 후면·측면 뷰에서 ArcFace가 얼굴을 못 찾는다(93장 중 7장).
  이것을 0.0으로 적으면 "이 세트에서 가장 나쁜 정체성"으로 읽힌다. 실제로는 **측정 불가**이므로 `None`이고
  페이지에는 `face —`로 나온다.

### 26.4 불변 export

`pipeline/export.py`. 명세 3.5의 요구를 그대로 구현했다:

- **불변 id** = 내용 sha256 앞 12자. 같은 내용이면 같은 id, 내용이 바뀌면 다른 id.
- **원자적 발행**: `.tmp-<pid>-<hex>` 스테이징 → `os.replace`. 검증 후 확정.
- **재사용**: 이미 온전한 id가 있으면 **다시 쓰지 않고 재사용**(`reused: true`). 손상된 것은 거부.
- **매니페스트**: 정책·상한·홀드아웃·이미지 목록·제외 사유 분포·흰배경 분포·캡션 정책·패밀리.

## 27. M5 GUI 통합 — 단계 버튼은 CLI를 부르고, 규칙은 CLI에만 둔다 (2026-11-06 20:10~20:30)

명세 M5는 "데이터셋 생성" 탭에 프로젝트 선택·단계별 버튼·로그·일시정지·취소를 넣고 **기존 탭은 바꾸지 말라**고
한다. 그래서 `automation/dataset_tab.py`에 탭 하나를 따로 만들고 `automation_gui.py`는 **12줄만** 고쳤다
(프레임·탭 등록·생성·import). 기존 세 탭의 코드 경로는 한 줄도 바뀌지 않았다.

### 27.1 왜 탭이 규칙을 다시 구현하지 않는가

단계 버튼은 자기 판단으로 무언가를 그리지 않고 `python -m pipeline.<모듈> <하위명령> --project <폴더>`를
그대로 실행한다(`stage_command`). 홀드아웃 제외·계보 상한·선택된 에포크·export 정책은 전부 파이프라인 모듈에
있고, 탭이 그것을 다시 적으면 두 진입점이 갈라지면서 **GUI가 규칙을 우회하는 길**이 된다.

탭이 스스로 판단하는 것은 **버튼을 회색으로 칠하는 일 하나뿐**이다. 에포크가 없으면 배치 B를 비활성으로 두는데,
이는 `batch_gen.character_lora_path`가 어차피 거부하기 때문이다(`BatchError: no epoch has been chosen…`).
회색은 GPU 작업을 큐에 넣은 뒤 실패하는 일을 줄이려는 것이고, 최종 거부는 여전히 CLI가 한다.

### 27.2 일시정지를 흉내내지 않았다

처음 작성한 탭은 `FIZGIG_STOP_FILE` 환경변수를 넘겼는데, **파이프라인이 그 변수를 읽지 않는다**. 즉 일시정지
버튼이 아무 일도 하지 않으면서 "요청됨"이라고 표시하는 상태였다. 대신 실제 배선을 추가했다:

- `pipeline/__init__.py`의 `make_cancel(stop_file)` — 파일 존재를 `cancel()` 콜백으로 바꾼다.
- `epochs.run`·`batch_gen.run`은 이미 `cancel` 인자를 받고 **칸 경계에서** 확인하고 있었다. CLI의 `main`이
  그 인자를 넘기지 않던 것뿐이라 `--cancel-file`을 추가해 연결했다(`fix`·`gen_qwen_edit`은 이미 지원).
- 탭은 `CANCELABLE = {"epochs","batch_gen","fix"}`에 있는 단계에서만 일시정지 버튼을 켠다. 나머지 단계는
  **취소만** 제공한다 — 멈출 수 없는 단계에 "일시정지됨"이라고 쓰면 죽인 프로세스를 정상 종료로 보고하는 셈이다.

테스트로 확인한 것: 취소를 걸면 그린 칸은 파일로 남고 나머지는 pending으로 남아 **재실행이 이어서** 그린다
(`epochs` 3칸 후 중단 → 재실행이 나머지 13칸, `batch_gen` 1칸 후 중단 → 재실행이 1칸).

### 27.3 실제로 돌려서 잡은 버그 3건

가짜 위젯 테스트만으로는 셋 다 안 잡혔다. 실제 Tk 창에서 실제 CLI를 돌려보고서야 드러났다.

**1. `ModuleNotFoundError: No module named 'pipeline'`** — 서브프로세스 `cwd`를 저장소 루트로 잡았는데
`pipeline` 패키지는 `automation/` 안에 있다. `cwd`를 `automation/`으로 고쳤다.

**2. `ModuleNotFoundError: No module named 'fizgig'`** — 1번을 고치자 다음 오류가 나왔다. 두 패키지가
**서로 다른 폴더**에 있어서(`pipeline`은 `automation/`, `fizgig`는 `src/`) 어느 한쪽 `cwd`로는 다른 쪽이 안 된다.
최종: `cwd`는 저장소 루트, `PYTHONPATH`에 `automation`과 `src`를 **둘 다** 넣는다.

**3. 일시정지했는데 "완료"라고 표시** — 일시정지 후 CLI가 **종료 코드 0**으로 끝나기 때문에 종료 코드만으로는
"다 그렸다"와 "멈췄다"를 구분할 수 없다. `pause_requested` 플래그를 두어
**취소 → "취소됨"**, **일시정지 + 종료 0 → "일시정지됨 · 다시 누르면 이어서"**, **종료 0 → "완료"**,
**그 외 → "실패 (종료 코드 N)"**으로 나눴다. 실패를 정상 정지로 보고하면 고장난 단계가 끝난 것처럼 보인다.

### 27.4 버튼 라벨이 동작과 달랐던 것

처음에는 "에포크 평가" 버튼 하나가 `epochs plan`만 실행했다. `epochs run`은 **`plan`이 쓴 manifest를 읽기만 하고
스스로 계획하지 않으므로**, 그 라벨은 GPU 시간을 썼는지에 대해 거짓말을 하는 셈이었다. 그래서 계획과 그리기를
분리해 12개 버튼으로 만들었다: `에포크 목록/계획/그리기/비교 시트`, `배치 B 계획/그리기`.
"그리기"·"실행"이라는 라벨이 붙은 버튼은 반드시 `run`을 부르는지 테스트가 확인한다.

### 27.5 일시정지는 실제로 동작한다(실측)

### 30.2 가중치는 w4a8을 골랐다 (VRAM 계산)

받아둔 세트가 두 벌이다. 워크플로 JSON은 **bf16 파일명**을 참조하지만 bf16은 없다.

| 세트 | DiT | TE | 업샘플러 | VAE | 합계 |
| --- | --- | --- | --- | --- | --- |
| int8_convrot | 19.76 | 4.77 | 9.08 | 2.93 | **36.5 GB** |
| w4a8 | 12.44 | 3.33 | 6.26 | 5.18(bf16) | **25.2 GB** |

VRAM 31.8 GB → **int8은 안 들어간다.** w4a8 + bf16 VAE를 `models\{diffusion_models,text_encoders,vae}`에 넣었다.
이 선택은 파라미터가 아니라 **모듈 상수**로 뒀다 — 잘못 고르는 건 품질 트레이드오프가 아니라 OOM이기 때문이다.

### 30.3 `ph3_gen.py` — 그래프를 직접 쓴 이유

P-H3는 krea2의 파라미터 변형이 아니다: 스텝 수 대신 **시그마 스케줄**을 쓰고, CFG가 없고, 프롬프트를 **두 번째
언어모델로 업샘플**하고, 참조 이미지를 9장까지 받는다. 그래서 `krea2_gen`에 끼워넣지 않고 새로 썼다(16~19노드).

측정값(이 박스, 1024×1536):

- 텍스트→이미지 **14.1초** (가중치가 이미 올라간 상태). 콜드 첫 호출은 25 GB 로딩 때문에 더 느리다.
- 시드를 바꾸면 **출력 해시가 달라진다**(`87e3950a…` vs `b77c3abd…`) — 스텁이 아니라 실제 샘플링이라는 증거.
- 참조 이미지 에디트: 19노드, 2.47 MB 출력.

거부하도록 만든 것 셋 — 모두 "조용히 그럴듯한 오답"이 나오는 경우다:

1. `sigmas_for()`는 **8스텝 외 길이를 거부**한다. 선형 보간하면 다른 곡선인데도 그림은 멀쩡히 나온다.
2. `check_references()`는 **로컬 경로를 거부**한다. ComfyUI도 거부하지만 몇 단계 뒤에, `Comfy.upload()`가 빠졌다는
   말 없이 거부한다.
3. `negative=` 인자를 **아예 없다.** `BasicGuider`에 negative 입력이 없어서, 받으면 아무 일도 안 하는 조작이 된다.

### 30.4 시드 정책 v2 — 생성기 목록을 정책의 속성으로

P-H3 산출물을 학습 입력으로도 쓰기로 했다. 그런데 `SEED_GENERATORS`는 모듈 상수라 직접 참조되고 있어서,
늘리려면 **이미 쓴 스냅샷까지 다시 읽히는** 구조였다. 그래서 정책의 속성으로 옮겼다:

```python
POLICY_GENERATORS = {"seed-v1": ("qwen_edit",),
                     "seed-v2": ("qwen_edit", "ph3_edit")}
```

`audit()`은 넘겨받은 정책에서 목록을 찾고, 기본값은 현재 정책이다. **모르는 정책은 최신 목록으로 폴백하지 않고
예외**를 낸다 — 그 폴백이야말로 옛 스냅샷의 의미를 조용히 바꾸는 경로다. 기존 스냅샷은 `seed-v1`로 그대로 남는다.

`lineage.GENERATORS`에도 `ph3_edit`을 넣었지만 **이건 다른 질문**이다: "그림이 P-H3 산출물이라고 정직하게 기록할
수 있나"이지 "시드셋에 들어가도 되나"가 아니다. 두 목록을 분리해둔 덕에 옛 스냅샷은 유효한 채로 새 엔진을 받아들인다.

### 30.5 `ph3_edit.py` — 실제 실행에서 나온 거부 규칙 둘

batch_gen의 P-H3 대응. 새로 그리는 게 아니라 **이미 캐릭터가 맞는 그림을 다른 구도로 재배치**한다. 그래서
`generator="ph3_edit"`, `edit_depth=1`, 원본을 부모로 기록한다.

실제로 돌려보고 **잘못된 계획 두 개**를 잡았다:

- **검수 대기 중인 슬롯을 또 그렸다.** 첫 계획이 8슬롯에 16장을 그리려 했다 — 슬롯마다 이미 1~2장이 검수 대기 중인데도.
  백로그를 줄이는 게 아니라 늘리는 짓이다. 판단을 순수 함수 `short_slots()`로 빼서 GPU 없이 테스트한다.
- **계보 없는 합성 앵커를 소스로 골랐다.** 첫 실제 에디트가 `origin=synthetic`·부모 없는 앵커에서 나왔고, 그 결과는
  `unverified_ancestor`로 **영원히 쓸 수 없는 그림**이 됐다. 검수로 고칠 수 있는 문제가 아니다. 이제 `sources()`가
  그런 앵커를 거부하고 이유를 남긴다(`unusable_sources`).

라이브 ComfyUI로 끝까지 검증: 강제 지정한 슬롯이 **26초/3.0 MB**로 생성 → depth-1 후보로 import →
**seed-v1은 `generator_not_eligible`로 거부, seed-v2는 수락(27→28장)**. 두 정책이 설계대로 갈리는 걸 확인한 셈이다.
검증용 그림 2장과 ComfyUI 업로드 3개는 그 뒤 제거했고, 프로젝트는 후보 104 / kept 27로 원상복구했다.
